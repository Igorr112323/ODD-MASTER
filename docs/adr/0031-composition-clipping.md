# ADR-0031: Отсечение состава контуром знака (Сазерленд—Ходжмен)

- **Статус:** принято (сессия 03).
- **Дата:** 2026-10-29.
- **Связано:** CR-22, ADR-0026, ADR-0028, M9-V01, M17-C01…C05.

## Контекст

Элементы состава — полосы, кресты, пучки — строятся как прямоугольники и по построению
выходят за поле знака (полоса «во всё поле» под 45° у 3.25/5.22/2.2). Раньше это лечилось
укорачиванием: `FitLength` ограничивал длину так, чтобы габарит прямоугольника влез в поле.
Для круга и ромба этого недостаточно — габарит вписан, а углы полосы торчат за контур («уши»
на превью 3.25, 5.22, 2.2 и в DXF вне знака).

## Решение

`OddMaster.Core.Geometry.PolygonClip` — отсечение многоугольника выпуклым контуром
(Сазерленд—Ходжмен), детерминированное, без зависимостей:

1. Наружный контур знака сводится к ломаной (`Flatten`, дуги по 15°).
2. Полоса отсекается этой ломаной; если пересечения нет — остаётся исходный прямоугольник
   (контур может быть незамкнутой кривой, тогда отсечение не применяется).
3. Порядок вершин результата сохраняется, повторяющиеся точки удаляются с допуском 1e-9.

Отсечение применяется **только к элементам состава**. Пиктограммы, кайма и поле не отсекаются:
это независимые слои, и отсечение там скрыло бы ошибку построения.

## Альтернативы

- Укорачивать полосу по габариту (как было): не помогает для круга/ромба, ошибка видна глазом.
- Рисовать полосы внутри круга по хорде: надо знать вид контура в каждом элементе — данные
  начали бы зависеть от формы знака.
- `clip-path` в SVG: не переносится в DXF/nanoCAD, то есть решает проблему только в одном приёмнике.

## Последствия

Плюсы: одинаково в SVG и DXF, форма знака берётся из контура, а не из данных; инвариант
M17-C05 ловит регрессию числом. Минусы: у 3.25 полосы теперь чуть короче хорды (отсечение
по ломаной с шагом 15°, погрешность ≈ 0,2 % радиуса); при большом числе полос число вершин растёт
(5 полос × 8 вершин вместо 5 × 4) — на 41 знаке это несущественно для DXF.
