# ADR-0029: Локальный оракул (.NET из песочницы) — границы применения

- **Статус:** принято (сессия 03, по CR-26.2).
- **Дата:** 2026-10-29.
- **Связано:** ADR-0020, E-024, E-039, E-040.

## Контекст

В песочнице агента нет официального .NET 8 и нет доступа к `api.nuget.org`/`dot.net`. Проверять
код без сборки нельзя. Исторически был собран локальный оракул: SDK 3.1 из npm-реестра плюс
самосборный OpenSSL 1.1.1w в `/tmp`. Формально это вне §11.2 (только официальный .NET 8),
фактически — единственный способ увидеть ошибки компиляции до пуша.

Сессия 03 показала и слабое место: оракул собран под C# 8 и не видит часть анализаторов .NET 8;
после перезапуска среды `/tmp` очищается, и оракул приходится собирать заново.

## Решение

Локальный оракул разрешён **только как инструмент песочницы**, с границами:

1. Никогда не попадает в репозиторий, в CI и в артефакты. Пути — только `/tmp`.
2. Финальное слово — CI на официальном .NET 8. Зелёный CI обязателен; локальная сборка его не заменяет.
3. Сгенерированные оракулом эталоны (SVG, DXF, отчёты) валидны только после зелёного CI.
   Практический приём: регенерация выполняется workflow `Regenerate` (ADR-0030), а не локально.
4. Оракул не может служить доказательством в отчёте: в отчётах — только CI-логи и артефакты CI.
5. Любая новая зависимость оракула (например, tree-sitter для синтаксической проверки) — тоже вне
   репозитория и не влияет на продукт.

## Альтернативы

- Работать «слепо» и узнавать об ошибках из CI: цикл 2–5 минут на итерацию, для 20+ правок неприемлемо.
- Затащить SDK в репозиторий: 100+ МБ бинарей в git, запрещено правилами и здравым смыслом.

## Последствия

Плюсы: быстрый цикл, меньше красных прогонов CI. Минусы: два разных компилятора могут расходиться
(в сессии 03 — `SignLayer` не найден netstandard-проектом: оракул собирал всё в одну сборку и не
видел проблему зависимостей); поэтому CI обязателен и остаётся единственным источником истины.
