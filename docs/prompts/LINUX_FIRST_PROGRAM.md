## Как запускать (для студента; агенту — к сведению)

1. Дождись конца текущей сессии агента. Если закоммитить файл в ту же ветку во время работы агента, будет конфликт пушей.
2. Сделай репозиторий **Private** (CR-01). Это обязательное условие до любых файлов из SDK nanoCAD (§6).
3. Положи этот файл в репозиторий: `docs/prompts/LINUX_FIRST_PROGRAM.md`.
4. Запусти новую сессию агента одной командой:

```
Прочитай docs/prompts/LINUX_FIRST_PROGRAM.md, docs/prompts/PRODUCT_PROGRAM_PROMPT.md,
все файлы docs/curator/ и docs/feedback/. Работай по LINUX_FIRST_PROGRAM.md до лимита
сессии, начиная с фазы F0. Отчёт — docs/reports/SESSION-NN.md по шаблону §11.
```

Продолжение следующих сессий — та же команда. Если агент не читает файлы из репозитория, вставь этот текст целиком.

## 0. Суть стратегии

Всё, что можно доказать без nanoCAD, ты доказываешь на Linux сам и автоматически. На Windows и в nanoCAD переносится только тонкий адаптер.

Переносится он не «на глаз», а через три проверяемых моста:

| Мост | Что переносит | Чем проверяется |
|---|---|---|
| М1. Контракт | Поведение САПР, на которое опирается ядро: документ, транзакции, отмена, события, ручки, хранение | Один набор контрактных кейсов. На Linux его гоняет xUnit против эмулятора, в nanoCAD — команда ODD_SELFTEST против настоящего хоста |
| М2. Эталонные снимки | Результат сценариев демо D1–D6 | Снимок, снятый на эмуляторе, — ожидаемый результат в nanoCAD. Студент присылает снимок из nanoCAD, CI сравнивает |
| М3. Сигнатуры SDK | Правильность вызовов MultiCAD .NET | Адаптер компилируется в CI против заглушек, сгенерированных из реального SDK пробой SdkProbe |

**Честная граница.** Linux не может доказать:

- поведение настоящего API;
- отрисовку в nanoCAD;
- хранение в DWG;
- скорость в САПР;
- ленту и меню.

Это закрывают только отчёты студента: SELFTEST, SNAPSHOT, скриншоты. Фраза «работает в nanoCAD» без ссылки на такой отчёт — ложь. Ложь в отчёте хуже несделанной работы.

## 1. Архитектура: четыре кольца

| Кольцо | Сборка | Что внутри | Где проверяется |
|---|---|---|---|
| 0. Ядро | OddMaster.Core (net8.0 + страховка netstandard2.0, CR-15) | Каталог, генератор, модель «Знак / Стойка / Ось», доменные команды и события, ведомость, контроль, Актуализатор, листы и легенда, подсказки Р 52289, ViewModel-и интерфейса | Linux + Windows CI |
| 1. Порты | OddMaster.Core/Ports/* | Интерфейсы, через которые ядро говорит с САПР | Контрактные кейсы |
| 2. Linux-хост | OddMaster.Host.Emulator | Строгий эмулятор САПР в памяти. Реализует все порты; выводит DXF/SVG/PNG (существующий DXF-стенд становится его «экраном»); хранение в JSON; сценарный ввод | Linux + Windows CI |
| 3. nanoCAD-хост | OddMaster.NanoCAD | Отображение портов на MultiCAD .NET. Никакой доменной логики: собрать ввод, вызвать доменную команду, нарисовать результат | Компиляция против заглушек (М3), ODD_SELFTEST у студента (М1, М2) |

### 1.1. Порты

Имена — предложение, минимум — то, что нужно D1–D6. Каждый порт — строка в `docs/ARCHITECTURE.md` и кейсы в контракте.

| Порт | Ответственность |
|---|---|
| ICadBackend | Есть (ADR-0025): примитивы, заливки, тексты, таблицы на вывод |
| ICadDocument | Создать, найти, изменить, удалить объект по непрозрачному дескриптору; транзакции; группы отмены |
| ICadEvents | Уведомления «изменён / удалён / отмена / повтор» и отложенная очередь пересчёта |
| ICadInteraction | Ввод для доменных команд: точка, объект, выбор из списка. В тестах — сценарий ввода |
| ICadGrips | Ручки доменных объектов. Решает ядро: где ручки и что значит перетаскивание. САПР только показывает |
| ICadPersistence | Сохранение данных объектов: версионированный набор свойств, миграции, кэш графики для «чужих» машин |
| ICadImport | Чтение старых чертежей для Актуализатора: DXF на Linux, DWG в nanoCAD |

### 1.2. Правила зависимостей — проверяются архитектурным тестом

- Ядро не ссылается ни на один хост.
- В ядре нет `OperatingSystem.*`, `RuntimeInformation.*` и `#if WINDOWS`.
- Адаптер nanoCAD ссылается только на ядро и SDK.
- Интерфейс построен по схеме ViewModel и View:
  - ViewModel (палитра знаков с поиском, отчёт Актуализатора, список нарушений) — в ядре и под тестами;
  - View (WPF/WinForms/Avalonia) — тонкая, только в кольце 3.

## 2. Строгий эмулятор: строже настоящей САПР

Эмулятор — тестовый дублёр, а не продукт. Его задача: код, прошедший эмулятор, должен с высокой вероятностью работать в nanoCAD. Поэтому эмулятор падает там, где настоящая САПР могла бы стерпеть.

| № | Семантика | Поведение эмулятора |
|---|---|---|
| 1 | Идентичность | Объект доступен только по непрозрачному дескриптору. Дескриптор удалённого объекта → исключение |
| 2 | Транзакции | Изменение вне транзакции → исключение. Abort восстанавливает состояние побайтно |
| 3 | Отмена и повтор | Одна доменная команда — одна группа отмены. «Команда → отмена» даёт снимок, равный исходному; «повтор» — равный результату |
| 4 | Повторный вход в событиях | Изменение объекта внутри его же уведомления → исключение. Пересчёты идут только через отложенную очередь после фиксации транзакции |
| 5 | Слияние событий | В одной транзакции «изменён» приходит один раз на объект |
| 6 | Хранение | «Сохранить → открыть» даёт равенство. Старая версия данных читается через миграцию. Неизвестная будущая версия → только чтение и предупреждение. Режим «модуль не загружен» показывает кэш графики |
| 7 | Культура | Все тесты идут дважды: ru-RU (десятичная запятая) и InvariantCulture. Кириллица в текстах объектов. Старые тексты для Актуализатора — в cp1251 |
| 8 | Пути и файлы | Только `Path.*`, никаких `/` в коде. Поиск файлов без учёта регистра. Терпимость к CRLF |
| 9 | Точность | Допуски сравнения — из конфига. Никаких `==` для double |
| 10 | Детерминизм | Один и тот же сценарий ввода даёт побайтно один и тот же снимок |
| 11 | Бюджет скорости | Сценарий «1000 стоек» и инкрементальное обновление ведомости укладываются в бюджет из конфига. Тот же замер идёт в ODD_SELFTEST |

**Предел.** Каждая возможность эмулятора появляется только под существующий контрактный кейс или сценарий. Никакого GUI, своего «движка САПР» и отрисовки сверх снимков DXF/SVG/PNG.

## 3. Мост М1 — контракт: один набор кейсов на два хоста

**Где лежит:** `src/OddMaster.Contracts`. Это библиотека без зависимости от xUnit. Кейс — данные плюс функция:

```csharp
// record — это C# 9. Если мешает локальный оракул на C# 8 (ADR-0029), сделай sealed class.
public sealed record ContractCase(string Id, string Port, string Title,
                                  Action<IHostUnderTest> Run);
```

**На Linux и Windows CI.** Кейсы прогоняются против эмулятора в `tests/OddMaster.Contracts.Tests` через xUnit `[Theory]` + `[MemberData]`. CR-03 в силе: xUnit — единственный раннер CI.

**В nanoCAD.** Команда `ODD_SELFTEST` исполняет те же кейсы против настоящего хоста. Она пишет `odd-selftest-ГГГГ-ММ-ДД.json`:

- версия nanoCAD;
- по каждому кейсу: id, pass, сообщение, время.

Это не замена xUnit: внутри САПР xUnit недоступен, и это исполнитель тех же кейсов.

**Отчёт студента.** Он коммитит отчёт в `docs/feedback/SELFTEST-ГГГГ-ММ-ДД.json`. Job CI `selftest-report` превращает его в таблицу в PR. Упавшие кейсы — задачи на следующую сессию.

**Стартовый список кейсов.** Минимум 20 до конца F2:

| Id | Кейс |
|---|---|
| C-DOC-001 | Создать → найти → удалить по дескриптору |
| C-DOC-002 | Дескриптор после удаления → ошибка |
| C-TRX-001 | Изменение вне транзакции → ошибка |
| C-TRX-002 | Abort восстанавливает состояние |
| C-UND-001 | Команда → отмена → снимок равен исходному |
| C-UND-002 | Повтор после отмены |
| C-EVT-001 | Одно «изменён» на объект за транзакцию |
| C-EVT-002 | Повторный вход отвергнут |
| C-EVT-003 | Отложенный пересчёт после фиксации |
| C-PER-001 | «Сохранить → открыть» для «Знак / Стойка / Ось» |
| C-PER-002 | Миграция старой версии данных |
| C-PER-003 | Кэш графики без модуля |
| C-GRP-001 | Перетащили ручку стойки → пикет и смещение пересчитаны |
| C-GRP-002 | Очерёдность знаков на стойке после перетаскивания не изменилась |
| C-AX-001 | Сдвиг оси на 50 м → пикеты всех стоек пересчитаны, журнал «до/после» записан |
| C-TAB-001 | Вставка знака → в ведомости ровно одно изменение, без полной перестройки |
| C-CHK-001 | Дубль на пикете найден |
| C-CHK-002 | Непарная табличка зоны найдена |
| C-CHK-003 | Знак вне границ найден |
| C-ACT-001 | Фикстура «2004» → ≥12 изменений в 6 категориях |
| C-CUL-001 | Под ru-RU числа читаются и пишутся без искажений |

## 4. Мост М2 — сценарии демо как исполняемые тесты и эталонные снимки

**Источник.** D1–D6 — строго по Программе §2.1. Каждый шаг — файл `scenarios/D?.json`:

- последовательность доменных команд;
- сценарный ввод: «клик» — это ввод точки или выбор объекта.

| Сценарий | Что доказывается на эмуляторе |
|---|---|
| D1 | Загрузка старой фикстуры «2004» (до гейта G4 — синтетика, после — образцы студента) |
| D2 | Стойки, знаки и таблички. После каждой вставки ведомость меняется инкрементально, промежуточные снимки сохраняются |
| D3 | Актуализатор: ≥12 замен, отчёт по 4 категориям брифа (+ служебные), обновлённая схема |
| D4 | Сдвиг оси на 50 м: стойки следуют за осью, журнал и ведомость пересчитаны |
| D5 | Контроль: дубль, непарная табличка, знак вне границ; у каждой находки есть ссылка на объект |
| D6 | Лист из шаблона: рамка и легенда из использованных знаков |

**Раннер на эмуляторе.** Он пишет нормализованный снимок `tests/golden/scenarios/D?.snapshot.json`:

- объекты без дескрипторов, в каноническом порядке;
- для каждого объекта: тип, слой, ключевые параметры, хеш геометрии с допуском;
- ведомость в CSV, журнал, находки контроля.

Плюс превью DXF/SVG/PNG «для глаз».

**В nanoCAD.** `ODD_SCENARIO D4` прогоняет тот же сценарий через настоящий хост, `ODD_SNAPSHOT` пишет снимок того же формата. Студент коммитит его в `docs/feedback/SNAPSHOT-D4-ГГГГ-ММ-ДД.json`. Job `cross-host-diff` сравнивает его с эталоном Linux; каждое расхождение — ошибка переноса с точным адресом.

Правила нормализации — в `docs/SNAPSHOT_FORMAT.md`:

- цвет — логическим именем;
- числа — с допуском;
- порядок не зависит от дескрипторов.

Снимок обязан быть одинаковым на Linux и Windows CI. Это уже первая проверка переносимости.

## 5. Windows без nanoCAD — GitHub Actions windows-latest

- **Тесты.** Все тесты ядра, контракта, эмулятора и сценариев — на Linux и на Windows, в культурах ru-RU и Invariant.
- **Адаптер.** Сборка против заглушек (§6) на обеих ОС.
- **Установщик.** Бесплатный инструмент на выбор (Inno Setup или WiX), выбор — ADR. Собирается в windows-latest.
  - Состав: DLL модуля, конфиги, справка.
  - Регистрация автозагрузки в nanoCAD — [ПРОВЕРИТЬ В SDK]. Пока не проверено, установщик копирует файлы и кладёт инструкцию ручной загрузки.
  - Артефакт CI: `OddMaster-Setup-<версия>.exe`.
- **Справка** — HTML из `docs/help/*.md`, собирается в CI.
- **Проба SDK.** CI публикует `SdkProbe.exe` как self-contained win-x64, чтобы студенту не ставить .NET.

## 6. Мост М3 — проба SDK → заглушки → адаптер

### Шаг 1 (ты, сейчас) — tools/SdkProbe

Консоль на net8.0 и `System.Reflection.MetadataLoadContext`.

- Вход: путь к папке nanoCAD.
- Список DLL — из `docs/SDK_ASSUMPTIONS.md` (SDK-001…008) плюс сборки с пространствами имён `Multicad*` [ПРОВЕРИТЬ В SDK].
- Выход в `sdk/` (DLL туда не попадают никогда):

| Файл | Содержание |
|---|---|
| sdk-meta.json | Версия nanoCAD; версии файлов; TargetFrameworkAttribute каждой DLL. Отсюда целевая платформа адаптера: net8.0-windows или net48 [ПРОВЕРИТЬ В SDK] |
| sdk-api.json + sdk-api.txt | Публичные типы и члены с сигнатурами, отсортированно |
| identity.json | Имя, версия и публичный ключ каждой сборки — для идентичности заглушек |

Тест пробы на Linux — на любых .NET-сборках, например своих: вывод детерминирован.

### Шаг 2 (студент, 10 минут)

Запустить `SdkProbe.exe "<папка nanoCAD 26>"` (путь [ПРОВЕРИТЬ]) и закоммитить `sdk/`. Только в Private-репозитории.

### Шаг 3 (ты) — tools/SdkStubGen

Работает на Linux, вход — `sdk-api.json`. Генерирует сборки-заглушки:

- те же имена, версии и публичный ключ (отложенная подпись открытым ключом);
- тела `throw null`;
- никакого кода и ресурсов SDK.

Если вся поверхность API слишком сложна — заглушки только для используемых членов. Решение — ADR.

### Шаг 4 (ты) — сборка адаптера

`OddMaster.NanoCAD` собирается с переключателем `-p:NanoCadSdk=stubs|real`:

- stubs — в CI;
- real — у студента: HintPath из переменной `NANOCAD_DIR`, `Private=false`, SDK-DLL в вывод не копируются.

Ошибки сигнатур ловишь ты сам, в CI.

**ГИПОТЕЗА, которую проверяет первый ODD_SELFTEST.** DLL, собранная против заглушек с той же идентичностью, загружается в настоящий nanoCAD. Если нет — запасной путь: студент собирает скриптом `scripts/build-nanocad.ps1` и коммитит лог в `docs/feedback/`.

**Лицензия.** Заглушки содержат только публичные сигнатуры. [ПРОВЕРИТЬ лицензию SDK nanoCAD на хранение сигнатур в приватном репозитории] — вопрос студенту в Q-NNN. Если лицензия запрещает — `sdk/` не коммитим, и работает запасной путь.

**До шага 2.** Код с угаданными именами MultiCAD — только в `src/OddMaster.NanoCAD/_draft/`. Эта папка исключена из сборки и в прогресс не засчитывается.

Вместо кода готовь `docs/SDK_NEEDS.md`:

| Порт | Что нужно от SDK | Гипотеза (SDK-NNN) | Кейсы контракта |
|---|---|---|---|

Как только появится `sdk/`, сопоставление займёт минуты, а не сессию.

**Self-hosted раннер больше не обязателен.** Компиляцию закрывают заглушки, поведение — ODD_SELFTEST. Раннер остаётся опцией на потом.

**Гейт G1 из Программы §4 переопределяется.** G1 открыт, когда студент закоммитил `sdk/` в Private-репозиторий. `RUNNER_READY.md` больше не нужен.

## 8. Фазы

Каждая фаза закрывается по приёмке. Незакрытое переходит в следующую сессию с пометкой.

### F0 — Долги и защита эталонов

Начинается первой.

1. Закрыть всё из `docs/curator/CURATOR-03.md` (CR-21…CR-26), если не закрыто.
2. **Эталон — закон.** Новый CI-страж: если в PR изменены `tests/golden/**` или `docs/demo/**`, а в `docs/visual/REVIEW-NN.md` нет записи с перечнем этих файлов, причиной и CR — job красный.
3. Workflow `[regen]`:
   - допустим только вместе с такой записью;
   - не переписывает эталоны, если падают тесты, не связанные с эталонами.
4. Регенерации сессии 03 перечислить задним числом в `REVIEW-03.md`.

**Приёмка:** страж краснеет на специально испорченной копии и зеленеет на честной.

### F1 — Порты, эмулятор, контракт

- Порты из §1.1 и архитектурный тест из §1.2.
- `OddMaster.Host.Emulator` с семантикой §2.
- `OddMaster.Contracts` и xUnit-обёртка.
- Кейсы C-DOC, C-TRX, C-UND, C-EVT, C-PER.

## 9. Железные правила — дополнение к Программе §11

1. **Никакого угаданного API.** Имена MultiCAD — только из `sdk/sdk-api.txt`. До него — только `_draft`. Каждое предположение — [ПРОВЕРИТЬ В SDK] и строка SDK-NNN.
2. **Ядро не знает ОС** (§1.2). Всё платформенное — только в кольце 3.
3. **Эталон — закон** (F0). Молчаливая регенерация — нарушение, равное подделке теста.
4. **Эмулятор — дублёр, а не продукт** (§2, предел). DXF — это «экран» эмулятора; лимит DXF-работ — 20 % сессии (CURATOR-03.md §5).
5. **Ошибка, найденная в nanoCAD,** превращается в новый кейс контракта или правило эмулятора. Без этого исправление не принимается.
6. **Один PR на сессию.** Нормативка — только с маркерами и статусами (Программа §7).
7. **Честность.** «Работает в nanoCAD» — только со ссылкой на SELFTEST/SNAPSHOT. «Работает на эмуляторе» — так и пиши: L1E.

## 10. Стоп-сигналы — дополнение к Программе §12

Остановиться и написать в отчёт, если:

- пишешь код MultiCAD вне `_draft` до появления `sdk/`;
- у эмулятора появляется возможность, которую не требует ни один кейс или сценарий;
- «живое» поведение показано только в DXF или на эмуляторе и подаётся как готовый продукт;
- эталоны меняются без записи в REVIEW;
- задача уходит за бриф: 3D, BIM, веб, «своя САПР», временная ОДД;
- работа над эмулятором или DXF занимает больше половины сессии, а D-сценарии не продвинулись.
