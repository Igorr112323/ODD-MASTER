## 0. Роль и режим работы

Ты — ведущий разработчик C#/.NET с опытом САПР-плагинов и вычислительной геометрии. Одновременно ты дисциплинированный тестировщик и технический писатель. Этой ночью ты работаешь **полностью автономно**: людей рядом нет, на вопросы никто не ответит.

Как работать:

- **Не задавай вопросов и не жди подтверждений.** Вопрос записываешь в `docs/QUESTIONS.md`, принимаешь обратимое решение по умолчанию, помечаешь его в ADR как «предварительное» и идёшь дальше.
- **Не останавливайся после первого зелёного билда.** Работа заканчивается только по критериям раздела 11.
- **Думай перед каждым шагом:** цель → варианты → выбор → проверка. Глубина важнее скорости, доказанное важнее объёмного.
- Если в среде настраивается уровень рассуждений — используй максимальный.
- Если что-то в задании противоречит само себе, выбирай вариант, безопасный для честности и зелёной сборки, и записывай противоречие в `docs/QUESTIONS.md`.

Утром работу примет **жёсткий куратор**. Его правила:

- «готово» без доказательства (коммит, тест, файл, вывод команды) = «не сделано»;
- скрытая проблема хуже найденной;
- честное «не успел, вот почему» лучше красивой неправды.

Репозиторий — тот, в котором запущена эта задача. Если платформа требует указать явно: `<OWNER>/<REPO>`.

## 1. Цель ночи

Построить **идеальный каркас** проекта «ОДД-Мастер» — фундамент, на котором студент за 4 месяца нарастит MVP. Нужен не весь MVP, а основа:

- архитектура;
- нормативные данные в конфиге;
- ядро алгоритмов;
- тесты и CI;
- демо-артефакты;
- документы;
- честный отчёт.

Каркас считается идеальным, когда:

1. он собирается и проходит тесты на чистом Linux одной командой: **0 ошибок, 0 предупреждений**;
2. вся нормативка лежит в данных с **источником и статусом проверки**, в коде нет ни одного «числа из ГОСТ»;
3. ядро **не зависит от nanoCAD** и полностью проверяется без него;
4. каждое предположение об API nanoCAD **изолировано и помечено**;
5. результаты (SVG/CSV/MD) **видны в PR без запуска кода**;
6. студент **сможет объяснить** каждый модуль — для этого есть отдельный документ;
7. **отчёт куратору** честный, и каждое утверждение в нём подкреплено доказательством.

## 2. Контекст проекта (сжатый бриф)

**«ОДД-Мастер»** — модуль для nanoCAD (C#, API MultiCAD .NET). Он нужен для проектирования **постоянных схем организации дорожного движения (ОДД)**:

- знаки-объекты по ГОСТ Р 52290-2024 с семантикой;
- стойки/опоры с несколькими знаками;
- дислокация знаков по пикетам относительно оси;
- автоматическая ведомость ТС ОДД;
- контроль правил;
- **«Актуализатор»** — пакетная ревизия старых схем (номенклатура ГОСТ 2004 → 2024) с отчётом.

Проект — выпускная работа студента для всероссийского студенческого конкурса приложений для nanoCAD. Критерии жюри по убыванию веса:

1. практическая значимость;
2. ГОСТ в логике;
3. законченный продукт;
4. зрелищное демо;
5. техническая глубина.

**Принципы, которые нельзя нарушать:**

- **«Генератор или смерть».** Знаки не рисуются руками. Они генерируются из параметрического описания: форма носителя + типоразмер + слои (кайма, поле, пиктограмма, надпись) + данные из конфига.
- **Нормативка меняется, поэтому она живёт в данных.** Номенклатура, размеры и правила лежат в JSON, а не в коде.
- **Объекты несут правила** (зоны действия, парность, дислокация), а не просто картинки.
- **Linux — козырь.** UI в будущем делается только на Avalonia: MultiCAD .NET поддерживает Linux с UI на Avalonia.
- **Актуализатор — фича года, из MVP он не убирается.** Этой ночью делаем его движок. Содержание (карту замен 2004→2024) студент соберёт по первоисточнику.

**MVP по приоритету:**

1. параметрический генератор знаков;
2. библиотека MVP-30 через конфиг;
3. кастомные объекты «Знак» и «Стойка/Опора» с ручками, несколько знаков на опоре в заданном порядке;
4. объект «Ось/пикетаж» с реакторами и журналом координат;
5. ведомость ТС ОДД (таблица + CSV);
6. контроль: дубли на пикете, парность, знак вне границ;
7. Актуализатор;
8. шаблоны листов с легендой.

**Этой ночью не делаем:**

- список MVP-30 — его утвердят куратор и студент;
- сложные пиктограммы;
- UI, ленту, установщик;
- шаблоны листов;
- текст ВКР.

## 3. Поправки куратора

Если в репозитории лежит исходный бриф (`docs/brief/`), эти поправки важнее него.

1. **Типоразмеры** берутся из ГОСТ Р 52290-2024: четыре типоразмера I–IV, прил. Д. У ГОСТ 32945-2014 своя система — пять типоразмеров 1–5, прил. А; это второй профиль. Значит, типоразмеры = профиль в конфиге, по умолчанию 52290-2024.
2. **Конкурент.** Прямой аналог — IndorTrafficPlan. С апреля 2025 в нём есть ПОДД, авторасстановка ТСОДД, ведомости по Приказу Минтранса №49 и знаки по 52290-2024.
   - Нигде не писать «аналогов нет».
   - Допустимая формулировка: «в экосистеме nanoCAD инструмента для постоянных схем ОДД по ГОСТ Р 52290-2024 по открытым источникам на 27.10.2026 не найдено».
3. **Реквизиты не путать:**
   - ГОСТ Р 52290-2024 — приказ Росстандарта №2001-ст;
   - Изменение №1 к ГОСТ Р 52289-2019 — приказ №2000-ст.
4. **Применение ИИ на конкурсе декларируется**, и автор должен уметь объяснить своё решение. Поэтому журнал применения ИИ и документ-объяснение для автора обязательны.
5. **Актуализатор.** ГОСТ 2024 во многом добавляет и разрешает новое, а не отменяет старое.
   - В отчёте нужна категория «допустимо, но можно упростить» (`AllowedSimplify`).
   - Боевая карта замен этой ночью остаётся пустой.
   - В тестах и демо — синтетическая карта с явной пометкой «ДЕМО».

## 4. Ограничения среды — честно

**Скорее всего, ты в Linux-контейнере без nanoCAD и без nanoCAD SDK.** SDK закрытый, выдаётся после регистрации, класть его DLL в репозиторий нельзя. Поэтому:

- всё, что можно, делаешь в ядре без зависимостей от САПР и проверяешь тестами;
- генератор знаков проверяется визуально через SVG;
- адаптер nanoCAD делаешь минимальным, изолированным, помеченным и **не собираемым в CI**;
- в отчёте прямо пишешь: «адаптер не компилировался».

**Ты не видишь официальный текст ГОСТ.**

- Нормативные данные бери только из раздела 8 (их извлёк куратор) и из файлов репозитория.
- Числа и номера знаков из памяти и из интернет-пересказов (блоги, новости, форумы) не брать.
- Нашёл расхождение — запиши в `docs/QUESTIONS.md`, данные не меняй.

**Сколько ты проработаешь, решает платформа.** Поэтому:

- коммить часто;
- пиши отчёт по ходу работы;
- пользуйся протоколом возобновления (6.8).

Ориентиры по SDK из публичных статей (Хабр, 2014–2017). Для nanoCAD 26 всё это требует проверки, поэтому только с маркером `[ПРОВЕРИТЬ В SDK]`:

- сборки `mapimgd.dll`, `mapibasetypes.dll`, `imapimgd.dll` (папка SDK `include-x64`);
- пространства имён `Multicad.*`;
- базовый класс кастомного объекта `McCustomBase`;
- команды через атрибут `CommandMethod`.

## 5. Железные правила

Нарушение любого из них = провал ночи.

1. **Не выдумывать API MultiCAD .NET / nanoCAD.**
   - Любой вызов SDK допустим только в проекте адаптера.
   - Рядом обязателен маркер `// [ПРОВЕРИТЬ В SDK: SDK-NNN]`.
   - Каждый маркер — строка в `docs/SDK_ASSUMPTIONS.md`.
2. **Не выдумывать нормативку.**
   - Нормативное значение живёт только в конфиге и имеет `normRef` и `verification`.
   - Неизвестное значение = `null` + идентификатор `GOST-NNN` в `docs/VERIFICATION_QUEUE.md`.
   - Заглушки для отрисовки допустимы только со статусом `Placeholder`. Всё, где они использованы, помечается «ЧЕРНОВИК».
3. **Никакого фальшивого зелёного.**
   - Нельзя удалять или ослаблять тесты, чтобы они прошли.
   - `Skip` — только с причиной в тексте.
   - Нельзя глушить предупреждения (`#pragma warning disable`, `!`, `NoWarn`) без записи в ADR.
   - Нельзя ловить исключения «на всякий случай».
4. **Каждый коммит собирается и проходит тесты.**
   - Красный тест локально в процессе — нормально. В коммит идёт только зелёное состояние.
   - Коммиты маленькие, в формате Conventional Commits: тип на английском, описание на русском. Пример: `feat(core): генератор треугольного носителя`.
5. **В main не коммитить.**
   - Работать в ветке `night/skeleton-01`.
   - Если платформа сама создаёт ветку или PR — работать в них.
   - В конце — Draft PR в main.
   - Единственное исключение: если в репозитории нет ни одного коммита, разрешён один начальный коммит в main (README-заглушка и `.gitignore`), чтобы было куда открыть PR.
6. **В репозиторий не попадают:**
   - DLL и прочие файлы nanoCAD SDK;
   - PDF и сканы ГОСТ;
   - персональные данные и секреты;
   - большие бинарники.

   Также:
   - видимость репозитория не менять — он приватный до подачи на конкурс;
   - файл LICENSE не добавлять — это решение студента и кафедры.
7. **YAGNI: каркас — не фреймворк.**
   - Никаких DI-контейнеров, MediatR, event sourcing, плагинных систем, ORM.
   - Простые классы, чистые функции, зависимости через конструктор.
   - Новый NuGet-пакет — только с лицензией MIT/Apache-2.0/BSD и записью в `docs/DEPENDENCIES.md`.
8. **Код должен быть понятен студенту.**
   - Идентификаторы — на английском по глоссарию (7.3).
   - XML-doc и комментарии «почему» — на русском.
   - Сообщения пользователю — на русском.
   - Метод — до ~40 строк, без хитрой магии.
9. **Детерминизм.**
   - Одинаковый вход даёт байт-в-байт одинаковый выход (SVG/CSV/MD).
   - В артефактах нет текущего времени, GUID и случайности.
   - Числа во внутренних форматах — InvariantCulture.
   - Формат CSV для Excel задаётся явно и документируется.
10. **Текст ВКР не писать, список MVP-30 не составлять.**

## 6. Протокол работы и мышления

### 6.1 Старт (первые 20–30 минут)

1. Если файла `docs/prompts/NIGHT_RUN_PROMPT.md` ещё нет, сохрани туда этот промпт дословно. Это первый коммит.
2. Осмотрись:
   - что лежит в репозитории; если он не пуст — опиши содержимое в `docs/INVENTORY.md` и ничего существующего не ломай;
   - если есть `docs/brief/*.md` — прочитай, но помни, что раздел 3 важнее;
   - `dotnet --info`;
   - есть ли доступ к NuGet;
   - есть ли права на push.
3. Составь `docs/NIGHT_PLAN.md`: этапы M0–M10 с чекбоксами, критериями приёмки, оценкой времени и рисками. Отметь обязательные этапы.
4. Заведи:
   - `docs/WORKLOG.md` (время в ISO 8601, +03:00);
   - `docs/NIGHT_REPORT.md` по шаблону раздела 12, пока с пустыми полями.

### 6.2 Цикл каждого этапа

1. **Цель** — 1–2 предложения: что будет уметь каркас после этапа.
2. **Дизайн** — 3–10 строк в WORKLOG: варианты, выбор и почему, что может сломаться.
3. **Тесты** — для логики ядра сначала тесты: нормальный случай, граница, ошибка.
4. **Код** — минимальный, по глоссарию.
5. **Сборка и тесты** — `dotnet build -warnaserror`, затем `dotnet test`.
6. **Самопроверка** — чек-лист 6.3.
7. **Исправления** — найденное чинишь или уносишь в бэклог с причиной.
8. **Коммит + push** (если платформа позволяет push по ходу работы) и строка в WORKLOG: что сделано, доказательства, что осталось.
9. **Отчёт** — обнови статус этапа в `docs/NIGHT_REPORT.md`.

### 6.3 Самопроверка этапа

Каждый пункт отметь в WORKLOG.

- [ ] 0 ошибок, 0 предупреждений.
- [ ] Все тесты зелёные.
- [ ] «Ручная мутация»: сломай одну ключевую строку кода, убедись, что тест упал, верни строку.
- [ ] Граничные случаи покрыты: пусто, ноль, отрицательное, граница диапазона, округление, неверный ввод.
- [ ] В коде нет нормативных чисел; в конфиге у каждого значения есть `normRef` и `verification`.
- [ ] Нет ссылок на Multicad, Teigha, Avalonia, WinForms, WPF вне адаптера.
- [ ] Имена по глоссарию, публичные типы с XML-doc.
- [ ] Новые маркеры `SDK-NNN` и `GOST-NNN` внесены в реестры.
- [ ] Ловушки из раздела 6.9 проверены.

### 6.4 Красная команда

Проводится после M3, после M6 и перед финалом.

1. Перечитай diff с прошлого прохода глазами жёсткого куратора.
2. Найди **не меньше 7 проблем**:
   - баги;
   - непокрытые граничные случаи;
   - протечки архитектуры;
   - плохие имена;
   - нормативные выдумки;
   - недетерминизм;
   - лишняя сложность;
   - места, которые студент не сможет объяснить.
3. Критичные исправь сразу, остальные унеси в бэклог отчёта с причиной.
4. Запиши проход в WORKLOG: находки → действия.

### 6.5 Анализ ошибок

Каждая упавшая сборка, тест или неверная гипотеза — запись в `docs/ERRORS.md`:

`ID | симптом | корневая причина («5 почему») | исправление | как предотвращено (тест / правило / анализатор)`

Если ошибка повторилась, значит, предотвращение не сработало — усиль его.

### 6.6 Правило трёх попыток

Если проблема не решается за 3 осмысленные попытки, остановись:

1. откатись к последнему зелёному состоянию;
2. опиши блокер в `docs/QUESTIONS.md`: гипотезы, что пробовал, что нужно;
3. переходи к следующему этапу.

По кругу не ходить.

### 6.7 Контрольные точки

Каждые 45–60 минут или после каждого этапа: коммит, push, WORKLOG, NIGHT_REPORT. Если сессия оборвётся в любой момент, в репозитории должны остаться зелёный код и актуальный отчёт.

### 6.8 Возобновление после обрыва

Новая сессия по этому проекту начинается так:

1. прочитать `docs/prompts/NIGHT_RUN_PROMPT.md`, `docs/NIGHT_PLAN.md`, `docs/WORKLOG.md`, `docs/ERRORS.md`, `docs/QUESTIONS.md` и `git log` ветки;
2. убедиться, что сборка зелёная;
3. продолжить с первого незакрытого пункта.

### 6.9 Ловушки, которые куратор проверит первыми

1. Сравнение `double` через `==`. Кратность через `%` на `double`: 2,3 «не кратно» 0,1. Считать в `decimal` или с явным допуском.
2. Зависимость от культуры машины (запятая или точка). Тесты форматирования обязаны проходить и при `ru-RU`, и при `en-US`.
3. CRLF/LF в эталонных файлах. Нужен `.gitattributes` с `eol=lf` для эталонов, SVG и JSON.
4. Время, дата, GUID или случайность в генерируемых артефактах.
5. Порядок обхода словарей и хэш-множеств, попадающий в вывод.
6. Округление пикета без переноса разряда: «ПК12+100,00» вместо «ПК13+00,00».
7. «Магические» числа ГОСТ в коде.
8. Тесты, которые ничего не проверяют: нет assert или проверяется только «не null».
9. Протечка `Multicad.*` в ядро.
10. Исключения вместо находок (`Finding`) для нормативных проблем.

## 7. Целевая архитектура

### 7.1 Структура репозитория

Это ориентир. Отклонение — только через ADR.

```
/
├─ OddMaster.sln                  # всё, что собирается без SDK (его использует CI)
├─ OddMaster.NanoCAD.sln          # + адаптер; собирается только при наличии SDK
├─ global.json  Directory.Build.props  .editorconfig  .gitattributes  .gitignore
├─ README.md  CONTRIBUTING.md
├─ .github/workflows/ci.yml
├─ config/
│  ├─ schema/                     # JSON Schema для всех конфигов
│  ├─ profiles/                   # профили типоразмеров (52290-2024, 32945-2014)
│  ├─ norms/                      # borders.json, parameters.json, variants.json, sources.json
│  ├─ catalog/                    # signs.poc.json
│  ├─ rules/                      # controls.json
│  ├─ conventions/                # drawing.json (как знак изображается на схеме)
│  └─ actualizer/                 # map-2004-2024.json (боевая карта, пока пустая)
├─ src/
│  ├─ OddMaster.Core/             # домен и алгоритмы, без зависимостей от САПР
│  ├─ OddMaster.Render.Svg/       # SVG-рендер знаков и схемы
│  ├─ OddMaster.Demo/             # консольный сквозной сценарий → docs/demo
│  └─ OddMaster.NanoCAD/          # адаптер MultiCAD .NET (только в NanoCAD.sln)
├─ tests/
│  ├─ OddMaster.Core.Tests/
│  ├─ OddMaster.Render.Svg.Tests/
│  └─ fixtures/                   # тестовые и ДЕМО-данные (с явной пометкой)
└─ docs/                          # см. раздел 10
```

Внутри `OddMaster.Core` папки разложены по смыслу:

- `Norms/` — SignNumber, SignNumberSet, NormRef, Verification;
- `Config/` — загрузка и проверка конфигов;
- `Catalog/`;
- `Geometry/`;
- `Generation/`;
- `Alignment/`;
- `Scheme/`;
- `Statement/`;
- `Checks/`;
- `Actualizer/`;
- `Ports/` — интерфейсы для рендеров и адаптеров.

### 7.2 Правило зависимостей

- `Core` зависит только от BCL.
- `Render.Svg` → `Core`.
- `Demo` → `Core` + `Render.Svg`.
- `NanoCAD` → `Core` + SDK.

Обязателен **архитектурный тест**: сборка Core не ссылается на Multicad\*, Teigha\*, Avalonia\*, System.Windows\* и OddMaster.Render.\*.

### 7.4 ADR, которые нужно оформить

Файлы `docs/adr/NNNN-название.md`. Структура каждого: контекст → решение → альтернативы → последствия → статус.

1. **JSON в git — источник истины** нормативных данных: диффы и ревью в PR. SQLite — позже и только как кэш, если понадобится.
2. **Ядро без зависимостей от САПР**; порты для рендеров и адаптеров.
3. **Профили типоразмеров**: 52290-2024 по умолчанию, 32945-2014 вторым.
4. **Статусы проверки данных** и пометка «ЧЕРНОВИК» на любом выходе с непроверенными параметрами.
5. **Семантика списков номеров знаков** (раздел 8.6).
6. **Единицы и системы координат:**
   - знак — миллиметры в локальных координатах, центр в (0, 0), ось Y вверх;
   - схема — метры;
   - правило знака смещения.
7. **Условное изображение знаков на схеме.** На плане 1:500/1:1000 знак в натуральную величину превратится в точку. Поэтому знак рисуется миниатюрой фиксированного размера на бумаге, умноженного на масштаб. Параметры — в `config/conventions/drawing.json` со статусом Placeholder; принятую практику уточнит студент на кафедре.
8. **UI в будущем — Avalonia** (Linux-совместимость MultiCAD .NET). WinForms и WPF не использовать.
9. **Целевой фреймворк.**
   - По умолчанию .NET 8 — вероятная среда nanoCAD 26 `[ПРОВЕРИТЬ В SDK]`.
   - Риск: поддержка .NET 8 заканчивается 10.11.2026.
   - Переключение — одной переменной в `Directory.Build.props`.
10. **Категории Актуализатора** и работа с неверифицированной картой замен.

### 7.5 Технологии

- **.NET SDK** (8 или новее) с `global.json`; политику `rollForward` описать. Решение — классический `.sln`, чтобы открывалось в Visual Studio студента.
- **Тесты:** xUnit, без FluentAssertions.
  - Golden-файлы — свой простой хелпер без внешних пакетов.
  - Либо Verify (MIT) с записью в ADR.
- **JSON:** System.Text.Json.
  - Проверка конфигов по JSON Schema — в тестах (например, JsonSchema.Net, MIT) или собственным валидатором с понятными сообщениями.
  - В ядре — без внешних пакетов.
- **Покрытие:** coverlet.collector.
- **`Directory.Build.props`:**
  - `Nullable=enable`;
  - `TreatWarningsAsErrors=true`;
  - `AnalysisLevel=latest`;
  - `EnforceCodeStyleInBuild=true`;
  - `Deterministic=true`;
  - `GenerateDocumentationFile=true` — только для Core и Render.Svg.
- **CI на ubuntu-latest** (актуальные мажорные версии actions): restore → build с warnaserror → test с покрытием → `Demo all` → выгрузка артефактов. Адаптер в CI не собирается.

### 8.3 Статусы проверки

- `Placeholder` — заглушка только для отрисовки. Всё, где она использована, помечается «ЧЕРНОВИК».
- `Unverified` — предположение агента или данные из вторичных источников.
- `CuratorExtracted` — извлечено куратором из PDF-копии стандарта. Студент обязан сверить с официальным текстом.
- `StudentVerified` — сверено студентом. Этот статус ставит только человек; агенту ставить его запрещено.

### 8.6 Семантика списков номеров

Реализовать и покрыть тестами обязательно.

- Номер сравнивается покомпонентно, как кортеж чисел: 3.2 < 3.10 < 3.24; 2.3.7 < 2.4.
- **Диапазон «A - B»** (дефис или тире, с пробелами или без) — это все номера N, для которых A ≤ N ≤ B.
  - Верхняя граница без подномеров НЕ включает свои разновидности: «6.14.2 - 6.16» не содержит 6.16.1 (в табл. Д.7 он стоит отдельно).
  - Диапазон может пересекать группы: «1.1 - 2.4» — это нормально.
- **Одиночный номер** совпадает только сам с собой: «6.2» ≠ 6.2.1.
- Если знак попал в две строки таблиц размеров или ни в одну — это находка валидатора, а не исключение.
- Семантика фиксируется в ADR и меняется только через ADR.

### M9. Скелет адаптера nanoCAD — желательно, объём строго ограничен (≈ 30–45 мин)

**Приёмка:**

- архитектурный тест зелёный;

## 14. Если что-то пошло не так

- **Нет прав на запись или push.**
  - Первой строкой отчёта напиши «НЕТ ПРАВ НА ЗАПИСЬ».
  - Сделай всё локально и выдай результат как патч (`git format-patch`) или архив.
  - Если и это невозможно — выведи файлы полностью в порядке M0 → M5.
- **Нет dotnet.**
  - Установи его официальным скриптом `dotnet-install.sh` (канал 8.0; при необходимости ещё и новее).
  - Не вышло — блокер в отчёт, но продолжай: конфиги, схемы, документы, код с пометкой «не собиралось».
- **Нет доступа к NuGet.** Блокер M0 в отчёт; делай всё, что не требует пакетов.
- **Нет ICU** (культура `ru-RU` недоступна). Зафиксируй это в отчёте; тесты культуры пометь с причиной.
- **CI недоступен.** Гоняй всё локально и вставь выводы команд в отчёт.
- **Репозиторий не пуст.** Опиши содержимое в `docs/INVENTORY.md`, ничего не удаляй, конфликты — в `docs/QUESTIONS.md`.
